# Local-first sync engine evaluation (#37)

**Status:** Research complete (Aug 2026) — **do not replace Yjs (#7) in production yet.**

## Context

FluxyChat already ships local-first patterns via:

| Layer | Implementation |
|-------|------------------|
| Message CRDT | `packages/sdk/src/message-crdt-yjs.ts` — Yjs message-list merge with REST |
| Room session | `room-session.ts` — optional `crdt-snapshot` merge on history load |
| Collab / whiteboard | `yjs-collab.ts` + Room DO `yjs-sync.js` |
| Merge conflicts | #48 — explicit conflict UI when LWW is ambiguous |
| Offline queue | SDK message delivery + reconnect in `react-native-sdk` |

The question: should we adopt a **dedicated sync engine** (ElectricSQL, PowerSync) instead of maintaining Yjs + custom merge?

## Options compared

### A. Keep Yjs + Room DO (current)

**Pros**

- Already integrated across web, worker DO persistence, game checkpoints, merge-conflict UX
- No new infra — fits Cloudflare Workers + D1 + DO model
- Apache 2.0 / MIT stack; no vendor sync SaaS required
- Fine-grained control over conflict detection (#48) and retention

**Cons**

- Team owns CRDT edge cases (snapshot size, tombstones, federation)
- No built-in SQLite replica on mobile — RN SDK uses REST/WS + local queue
- Scaling collab docs requires DO snapshot discipline (`YJS_SNAPSHOT_POLICY`)

**Verdict:** **Best fit for 2026 production.** Lowest risk; incremental improvements only.

### B. ElectricSQL

**Pros**

- Postgres ↔ local SQLite sync with reactive queries
- Strong local-first DX for read-heavy apps

**Cons**

- **Requires Postgres** (or compatible) as source of truth — FluxyChat is **D1 + DO**, not PG
- Sync service is additional ops (self-host or Electric Cloud)
- Message fan-out and presence still need Room DO — sync engine does not replace realtime path
- Migration cost: rewrite message storage model

**Verdict:** **Not recommended** unless FluxyChat moves primary message store to Postgres/Hyperdrive with a clear multi-year bet.

### C. PowerSync

**Pros**

- SQLite on device + sync rules against backend DB
- Good RN/mobile story; used in offline-first mobile apps

**Cons**

- Backend must expose sync-compatible source (typically Postgres)
- Sync rules + conflict policy overlap with existing Yjs merge work
- Commercial tiers for scale; self-host adds complexity
- Same architectural mismatch as ElectricSQL for D1-centric edge stack

**Verdict:** **Defer.** Revisit if we ship a **Postgres-backed tenant tier** and need native SQLite on mobile without custom merge.

## Decision

| Question | Answer |
|----------|--------|
| Replace Yjs now? | **No** |
| Next incremental step | Harden Yjs snapshot policy, expand RN offline queue tests, monitor merge-conflict rate |
| Trigger to re-evaluate | (1) PG migration for messages, (2) >15% ambiguous merge rate, (3) mobile offline SLA requiring SQLite replica |
| Priority | 🟢 Research — **closed for 2026** |

## Recommended follow-ups (non-blocking)

1. Document Yjs snapshot limits in tenant ops runbook (already in `YJS_SNAPSHOT_POLICY`).
2. Add RN E2E test for offline send → reconnect → merge (extend `react-native-sdk` tests).
3. Track `message_merge_conflicts` table growth — if spikes, invest in #48 V2 thresholds before new engines.
